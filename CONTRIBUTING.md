# Contributing to LLFIO

Thank you for your interest in contributing to LLFIO! This document covers the
basics of how to get a change accepted.

## Before you start

- Check open [issues](https://github.com/ned14/llfio/issues) and
  [pull requests](https://github.com/ned14/llfio/pulls) to avoid duplicating
  work already in progress.
- For anything non-trivial (new features, API changes, architectural changes),
  please open an issue first to discuss the approach before writing code.
- Small fixes (typos, docs, obvious bugs) can go straight to a pull request.

## Getting the source

Fork the repository on GitHub, then clone your fork (a git clone is required,
a zip/tarball snapshot will not let you open a pull request):

```bash
git clone --recursive https://github.com/<your-username>/llfio.git
cd llfio
```

If you already cloned without `--recursive`:

```bash
git submodule update --init --recursive
```

## Branching

Base new work on the **`develop`** branch, not `master`:

```bash
git checkout develop
git pull
git checkout -b my-feature-branch
```

Open pull requests against `ned14/llfio:develop`.

## Building and testing

See [Build.md](Build.md) for full build instructions. Quick reference:

```bash
mkdir build && cd build
cmake -DCMAKE_BUILD_TYPE=Release ..
cmake --build _hl -j$(nproc)     # header-only test/example suite
cmake --build _sl -j$(nproc)     # static library tests
cmake --build _dl -j$(nproc)     # shared library tests
ctest -R llfio_hl --output-on-failure
```

For a CI-equivalent run: `ctest -S .ci.cmake`.

## Code style

- All source, header, and test files target **C++ 17**. Do not use later
  standard features unless guarded by feature-test macros (the codebase has
  existing preprocessor macro infrastructure for this — reuse it where
  possible).
- Run `clang-format` on every changed header/source file before submitting
  (do not run it on CMake files). If you have Python and
  [pre-commit](https://pre-commit.com) installed, running
  `pre-commit install` once will do this automatically on `git commit`.
- New implementation work belongs under `include/llfio/v2.0/`; the top-level
  `include/llfio/` headers are legacy re-exports and should not be edited
  directly.
- The `attic/` and `single-header/` directories are legacy/auxiliary; you
  normally won't need to touch them.

## Adding tests

- New unit tests go in `test/tests/`; register the source path in
  `llfio_TESTS` inside `cmake/tests.cmake`.
- New compile-test examples go in `example/`; register the path in
  `llfio_COMPILE_TESTS` inside `cmake/tests.cmake`.
- Both lists are hand-maintained — the "DO NOT EDIT, GENERATED BY SCRIPT"
  header comments in that file do not apply to the list contents.

## Submitting a pull request

- Keep pull requests focused on a single change; unrelated cleanup makes
  review harder.
- Make sure your branch builds and the relevant test targets pass locally
  before opening the PR.
- Describe *what* changed and *why* in the PR description; link any related
  issue.
- By submitting a contribution, you agree it is licensed under the same dual
  Apache License 2.0 / Boost Software License 1.0 terms as the rest of the
  project (see [Licence.txt](Licence.txt) and [NOTICE](NOTICE)), unless you
  state otherwise in the pull request.

## Reporting bugs

Please open a [GitHub issue](https://github.com/ned14/llfio/issues/new) with:
- A minimal reproduction (compiler, OS, LLFIO commit/version).
- Expected vs. actual behaviour.
- Any relevant error output.

For security vulnerabilities, see [SECURITY.md](SECURITY.md) instead of
opening a public issue.
